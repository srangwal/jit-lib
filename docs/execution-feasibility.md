Initial experiments: 2026-09-20, America/Los_Angeles. Direction updated: 2026-09-23.

Just-in-Time Library will ask agents to modify a library and then evaluate the result. Before implementing the generator, we must establish two things: the agent can perform useful work, and neither the agent nor its generated code can falsify acceptance. This report records the small experiments used to investigate those questions in Phase 2 of the [execution plan](execution-plan.md).

Separate-process checks protect selected test subsets. Full-suite investigation exposed lost shared YAML objects and changed recursion behavior. These are research experiments, not generator implementation or real specializations. They establish no performance target. The [scope](scope.md) records the current milestone and later requirements. ## The problem in plain terms

A library produces answers; tests judge those answers. If both run in the same Python interpreter, library code can sometimes change the machinery doing the judging. A container around that whole interpreter protects the host, but does not separate the library from its test runner.

Our experiments place assertions in a **trusted parent process** and candidate library code in a restricted **worker process**. A small test-only **adapter**, also called a facade, forwards allowed calls and returns data. The worker cannot decide the test verdict. For a simple function this worked. For real libraries, the interface also includes shared mutable objects and **callbacks**: application functions that the library invokes during processing. Copying those objects can change behavior; passing unrestricted live objects can give the worker access to the checker.

The unresolved question is therefore whether we can preserve the required application's normal interactions while keeping its assertions outside candidate control. The adapter is test instrumentation. It is not a proposed new runtime interface for the delivered application.

A **probe** below is one limited experiment. A **fixture** is the small synthetic application used by several probes. A **mutant** is a deliberately altered implementation used to test whether a defense rejects an error or attack. None of these variants is evidence that the live coding agent spontaneously attempted to cheat.

## Confirmed requirement: protect repository-test execution

An ordinary repository test imports the library into the runner process. Our attack variant replaced `unittest.TestCase.run` in that process. The replacement announced success for each test without calling its body. Test files stayed read-only and unchanged; the change occurred in memory. This explains why container/file protection alone did not protect assertions.

The more revealing variant kept normal library answers correct. All six external replays matched, yet a deliberately failing test falsely passed and the four-test suite reported success without running its bodies. The same deliberate failure failed against the original. Correct replay output therefore could not establish that the repository assertions had run.

The user confirmed that v1 must protect repository assertions too. We cannot reclassify these suites as untrusted supporting evidence to bypass that requirement. The required setup must keep a deliberate failure from becoming success without changing/skipping tests or changing supported behavior. The delivered library must still use its normal runtime interface.

There is no ambiguity about this requirement. The unresolved work is technical: demonstrate it for the real pairs. Continue the authorized boundary research before implementing the dependent generator; do not relax the requirement.

A separate problem is code that runs honest tests but violates behavior the tests forgot to check. Specification-aware auditing means reviewing the candidate against intended behavior and constructing counterexamples to such omissions. The user confirmed that validated, mandatory development checks may grow during search, with candidate eligibility rechecked, while final evaluation stays frozen. A finding requiring changes to the frozen contract ends the run and requires a new audited run. The [updated SkyDiscover assessment](skydiscover-assessment.md#specification-aware-auditing-and-reward-hacking) records the paper, its relationship to this boundary, and the helper experiment. Candidate auditing has not yet been executed for this project, and the helper probe does not claim to evaluate the full upstream auditor. Neither this policy decision nor the helper experiment closes the assertion-isolation gap.

## Narrow protected-assertion result

The `scripts/protected_tests.py` experiment runs unchanged fixture tests in a parent that never imports candidate code. Its adapter supports only `summarize(list[str])`: send the strings to a fresh restricted container, accept a bounded JSON result, reconstruct ordinary data, then run the assertion in the parent. Missing/malformed output, fake verdicts, excessive output, and hangs are rejected. Both the original and the output-preserving attacker reach an added failing assertion after the library call, and both fail. The parent runner and protected source remain unchanged.

The independent rerun used the Python-only image with Codex absent from the host command path. Its first attempt caught an accidental bytecode-cache write by the host test loader; it failed the unchanged-tree check. The harness now disables that write. The original script and failure were preserved, the harness-created cache removed, and the rerun passed. See `provenance/protected-tests-reproduction.json`, `provenance/protected-tests-bytecode-fix.json`, and `provenance/protected-tests-reproduction-2.json`. This was a harness side effect, not a candidate attack or evidence of model intent.

The report says `fixture_boundary_passed: true` but `phase2_gate_satisfied: false`. A string-list function does not test persistent state, callbacks, subclassing, or shared objects. In particular, object identity means two references point to the same object, so mutations through one reference must appear through the other. PyYAML and Markdown expose richer interfaces than this bridge supports. No complete real-pair suite ran through it, and startup/message costs are not speedup measurements. See [F-02](reward-hacking-findings.md#f-02-separating-assertions-from-candidate-execution-defeats-the-fixture-attack) for details.

## Full-suite inventory and new compatibility failures

The latest investigation records every test in the qualified suites instead of selecting another convenient subset. The yamllint/PyYAML inventory reran the original 430 application tests and 1,283 pure-Python library tests successfully, without skips. The MkDocs/Markdown inventory collected 724 application tests with four declared skips and 1,088 library tests with twelve declared skips. Collection is not execution; these inventories do not establish protected full-suite results. No additional tests were excluded.

The inventory found interfaces beyond text conversion: persistent loader state, token classes, exception fields, import-time resolver registration, locally defined subclasses, registries, actual builtin types, streams, mocks, callbacks, and CLI subprocesses. It also identified assertions inside Markdown's own `test_tools` module. That module must be treated as protected evaluator support even though it is distributed within the library package. The external [YAML assessment](/private/tmp/jit-lib-feasibility.2__rqrwc/experiment/pyyaml-full-protection-assessment.md) and [Markdown assessment](/private/tmp/jit-lib-feasibility.2__rqrwc/experiment/mkdocs-full-interface-assessment.md) list source locations, test identities, and reproduction commands.

Two executed counterexamples show why a larger message schema alone is not yet a solution:

- **YAML shared objects:** loading two aliases directly produces references to one list; the existing JSON facade produces two copies. Mutation through one reference is then invisible through the other. A recursive list also fails to cross that facade. [F-13](reward-hacking-findings.md#f-13-the-yaml-adapter-loses-shared-and-recursive-values) records both cases and the host/worker version mismatch.
- **Markdown interpreter state:** one unchanged upstream test expects five nested blockquotes. Direct original execution passes, but an original-library worker produces ten; forwarding the parent's numeric recursion limit still produces eight. Both processes use the exact same Python executable. Markdown measures the actual call stack, which moving work into a process changes. [F-14](reward-hacking-findings.md#f-14-moving-markdown-to-a-worker-changes-an-existing-recursion-test) records the original assertion failures and the earlier instrumentation error.

Stable identifiers for remote objects may help preserve aliases and mutation. They do not by themselves preserve subclasses, Python runtime context, or safe execution of application-owned methods. Allowing unrestricted operations on parent objects would require a separate authority analysis; it cannot be assumed safe merely because messages are validated JSON.

These findings reject the current narrow adapters as a completed full-suite solution. They do not prove that stronger protected execution is impossible. On 2026-09-21, the user selected **direction 1: retain broad library-code editing and investigate stronger protected execution**. Restricting candidates to a predefined transformation family is not the selected approach. No weaker assertion requirement, replacement application runtime, or reduced test suite has been adopted.

Phase 2 still needs an actual implementation of a suitable protection mechanism, faithful execution of the required real suites, active forgery controls that remain failures, and independent reproduction of that complete arrangement. The first checkpoints investigated shared-object transport and observed runtime context without special-casing expected answers; their results follow below. Independent reviews identify the common integration and result-capture design still needed. Adding the completed mechanisms to an adapter does not automatically preserve every Python interaction.

## Direction 1: progress toward stronger protected execution

The shared-object experiment now preserves the tested YAML aliases and cycles, together with Markdown metadata identity and mutation across calls. Original and output-preserving forgery variants pass the five unchanged metadata tests; wrong output fails four. Thirteen malformed-message controls reject their inputs. Independent reruns reproduce these results both with ordinary subprocesses and with restricted Linux containers. Each container run verifies cleanup of all 23 workers. The representation remains restricted to bounded builtin container graphs. [F-16](reward-hacking-findings.md#f-16-shared-object-transport-must-not-make-evaluator-evidence-shared-too) records the tested domain, environment differences, and remaining limits.

Review found a new evaluator defect during this work: saving a shared result dictionary directly into a report lets a later valid graph message alter the earlier evidence. The corrected prototype detaches recorded evidence while preserving live aliases for application state. Another control confirms that a test catching a communication exception cannot erase the separately recorded infrastructure failure. These are distinct requirements from preserving the library's output values.

The recursion experiment now has a limited positive result. Measuring the remaining recursion budget at the caller and preserving that budget at the selected worker method makes the unchanged Markdown nesting test pass across nine caller/worker depth combinations. Another 36 comparisons match direct original output and budget. An independently repeated run confirms those results and rejects an actual changed candidate output. The mechanism uses measured context, not expected answers. [F-15](reward-hacking-findings.md#f-15-measured-recursion-context-preserves-one-test-family-with-observable-limits) explains the calculation and evidence.

This experiment also makes the remaining problem precise. Budget transfer changes the absolute recursion limit. Adding wrapper frames preserves both numeric values in 27 cases, but explicitly cannot handle 18 cases where the worker stack is already deeper. Neither approach recreates real caller frames. Imports and object construction occur before the adjustment, and the profiling hook is not protected against candidate interference. This is an ordinary-process behavior experiment, not the complete security boundary.

The [independent architecture review](/private/tmp/jit-lib-feasibility.2__rqrwc/experiment/direction1-architecture-review.md) distinguishes three research paths: extend the restricted CPython worker with explicit object/context rules; investigate another runtime's existing sandbox machinery; or build a testing interpreter that enforces ownership of objects. None is established as a complete solution or adopted as the delivered application runtime.

The inheritance checkpoint now passes the seven unchanged Markdown extension-class tests that the earlier adapter could not support. Actual selected-library methods run in the worker; a caller-owned override runs in the parent and can make a nested base-method call. Added controls preserve tested aliases, state changes, and ordinary exception handling. Nine deliberate assertion failures remain failures, including against a worker that catches callback exceptions. Twelve caught protocol/encoding failures remain ineligible even when their test bodies pass. The 39-case experiment comprises 69 test executions per run and has independent ordinary-process and restricted-container repetitions. Each container run removes all 59 containers. Its added mandatory callback assertions use an explicit marker; it does not automatically classify every existing test's assertion. Two subsequent ordinary-process experiments address further interactions. The PyYAML checkpoint preserves nested selected base-method execution and caller-owned custom objects in reduced fixtures with original class bodies; it is not a complete upstream test run. The Markdown checkpoint connects an unchanged serializer-registration test to actual selected rendering in one session, with input-dependent callbacks and persistent registration. Both have independent reproductions and reject deliberately broken selected code. [F-18](reward-hacking-findings.md#f-18-caller-defined-classes-need-more-than-copied-values) and [F-19](reward-hacking-findings.md#f-19-extension-registration-and-rendering-must-work-in-the-same-session) record the results and remaining incompatibilities.

The [cross-protocol review](/private/tmp/jit-lib-feasibility.2__rqrwc/experiment/cross-protocol-protection-assessment.md) and [PyYAML full-suite review](/private/tmp/jit-lib-feasibility.2__rqrwc/experiment/full-suite-integration-assessment.md) identify the common design needed before further expansion. They also distinguish message validation from faithful capture of an actual selected-library result. The latter remains an unestablished trust assumption; the proposed adversarial experiment was blocked before code or results were produced. The remaining work can be understood as five questions:

| Question | Evidence we still need |
| --- | --- |
| Does the separation preserve normal Python interactions? | A combined arrangement covering the inventoried classes, callbacks, shared state, exceptions, streams, mocks, interpreter context, and application subprocesses. Separate successful demonstrations do not establish that these mechanisms work together. |
| Do received values faithfully represent what the selected library returned? | A result-capture mechanism outside candidate authority, or another independently justified correspondence check. Message shape, source-file hashes, and OS isolation do not alone establish this property. |
| Can the candidate use permitted messages to change the judge? | Explicit rules about which parent objects and operations each request may affect, with adversarial checks of parsing, callbacks, shared data, and recorded evidence. Operating-system isolation alone does not validate those rules. |
| Do all required tests still run faithfully? | Complete protected runs with the same collected tests and existing skips as the qualified reference, using the actual selected candidate throughout. Deliberately failing assertions must remain failures. |
| Can someone else reproduce the complete result? | Standalone instructions and an independent rerun of the combined mechanism, full suites, and active forgery controls. The existing independent reruns cover only their named experiments. |

Phase 2 is complete only when these questions have satisfactory execution evidence. A choice of research direction or another small passing subset does not satisfy that condition.

## Authorized investigation: a separate engine for correctness tests

The user authorized investigating a different Python engine for protected correctness testing. Normal application delivery and all performance measurements remain on CPython. GraalPy is the first source-reviewed option; authorization to investigate it is not a decision to adopt it.

The investigation has three separate gates:

| Gate | Required evidence |
| --- | --- |
| Runtime and restrictions | Identify exact release artifacts and prerequisites, start the intended restricted configuration, and verify its declared access settings. Preserve failed startup attempts. Do not quietly enable native or host access to make a check pass. |
| Faithful host-owned observations | Demonstrate ordinary Python calls and result capture through code outside candidate authority. Distinguish the Python object's behavior from any custom behavior its interoperability interface presents to another language. A host-owned encoder alone does not establish that correspondence. |
| Compatibility and protected execution | Compare unchanged original tests, collection IDs, existing skips, types, state, callbacks, streams, and recursion behavior with the CPython references. Ordinary suites running together in one guest interpreter are compatibility evidence only; assertions still need their own demonstrated protection boundary. |

Begin with small semantic checks and the existing recursion-sensitive and API tests before attempting the complete suites. Retain wrong-result and missing-work controls appropriate to each mechanism, without changing original expected results or excluding incompatible tests. Record exact commands, environments, source identities, results, and independent reproduction instructions in the external experiment directory. No speedup claim follows from these checks.

The first two bounded checks now have execution evidence on macOS arm64. GraalPy Community 25.2.4 reports Python 3.12.8 and starts with `SandboxPolicy.UNTRUSTED`, guest native/process/network/filesystem access disabled, and explicit resource limits. Java receives and checks a number and a string. An independent repeat produces the same result. This establishes acceptance of the recorded configuration and these calls; the limits were not deliberately exhausted, and a printed policy label is not an independent security attestation.

All 15 benign object/callback checks also pass in an independent repeat. Java retains the exercised aliases, cycles, and class identities and sees Python mutation. The experiment deliberately gives one callable different Python and foreign-language behavior: Python produces `Hello Ada`, while its documented Java-call interface produces `HELLO ADA`. Both are correct for their respective interfaces. Thus a protected Java checker still needs to choose operations that correspond to the Python behavior being tested. See [F-21](reward-hacking-findings.md#f-21-a-protected-host-still-needs-faithful-python-operations).

GraalPy also passes the unchanged recursion test and all 88 Markdown API tests, with exact reference test IDs, no skips/errors/failures, and unchanged frozen source/dependency hashes. The compatibility profile adds read-only original sources/dependencies and a dedicated writable temporary directory; it retains the strict policy and disables native access. These assertions and original library code share one Python context, so the result establishes bounded compatibility, not protected assertions. The complete suites were not run. The [compatibility README](/private/tmp/jit-lib-feasibility.2__rqrwc/experiment/graalpy-compatibility/README.md) records environment differences, including GraalPy's pure-Python PyYAML dependency versus the CPython reference's LibYAML-enabled dependency and the embedded engine's empty `sys.executable`.

The separate-context experiment exposes why that distinction matters. Ten normal observations pass when the small class/list/callback fixture stays in one context. With two separately created restricted contexts, aliases, list mutation, base construction, and a callback still work. However, the foreign list is no longer exactly the local Python `list` type, and the combined subclass/override/`super()` operation raises `RecursionError`. Three dependent class checks consequently do not run. This is an executed mismatch for this arrangement, not a proof that every stronger design is impossible. No facade or fallback was added to hide it.

Startup and the 15 capture checks have independent repetitions. The original-suite and two-context checks have implementer execution and controller source/result review; they have not been independently rerun. The [runtime README](/private/tmp/jit-lib-feasibility.2__rqrwc/experiment/runtime/graalpy-25.2.4/README.md) and [capture README](/private/tmp/jit-lib-feasibility.2__rqrwc/experiment/graalpy-capture/README.md) preserve commands, hashes, results, setup failures, and standalone reproduction. The user requested a pause after these three parallel tasks; no next investigation or full-suite expansion was started. Phase 2 remains open.

## Consequences for design and SkyDiscover reuse

The successful parts support separating task descriptions, product-specific agent invocation, exact candidate snapshots, and controller-owned evaluation. This exercises the agent-neutral pattern proposed in the [SkyDiscover assessment](skydiscover-assessment.md) through a direct Codex path. No SkyDiscover adapter, execution helper, package, search algorithm, or nine-role topology was adopted. AdaEvolve integration and any comparison remain unexecuted.

Retain these findings when resolving the design:

- Parse process status and structured agent completion separately. Neither is a correctness verdict.
- Keep protected material and its copies out of generation mounts, context, logs, and reusable agent state. The temporary authentication/runtime directories were removed; no real credentials are included in the evidence.
- Use separately executed candidate/build processes, externally owned comparisons and clocks, and whole-container teardown. Copy and identify candidates only after their generation container is gone; an unfinished task remains ineligible.
- Do not promote a repository runner's success message into proof that its assertions ran. Resolve the demonstrated gap before finalizing acceptance responsibilities.
- Keep standalone evaluation independent of Codex and search code. The exported fixture verification uses neither.

The Linux baseline runs establish original build/test compatibility for the recorded environment. They do not establish full protected candidate execution, automatic experiment construction, comprehensive behavioral coverage, secure execution against every possible attack, or statistical performance measurement. The external clock includes container/process startup and gives no speedup estimate. Phase 3 still needs to settle exactly which work to time, limits, and confidence intervals.
